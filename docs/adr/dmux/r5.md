## Corrections — 2026-08-19, after P11

Everything above stands as written: it records what was believed at the close of r5.
Several of its claims stopped being true within a day, and the first is destructive to
act on. Verified against both hosts and both live registries — read-only, on copies —
on 2026-08-19.

**`~/.zshenv` is load-bearing, not cleanup.** `rm ~/.zshenv` today breaks remote dmux
on both machines. `cc3946e` tracks it at `shared/zsh/.zshenv`, maps it to `~/.zshenv`
in `config/targets.dotfile`, and both hosts symlink it. `.zshrc` is the only other
tracked zsh entry point and non-interactive zsh never reads it, so with `~/.local/bin`
added only from `conf.d` the remote agent — which runs as `ssh <host> dmux _agent …` —
cannot find `dmux` at all. That is the `command not found`, exit 6, on
`dmux ssh fredrir@10.77.77.1` from Archie: Macie's untracked `~/.zshenv` sourced
`. "$HOME/.cargo/env"` and nothing else. The same commit moves `~/.cargo/bin` into
`macos/zsh/conf.d/21-paths.macos.zsh`, because that one source line was its only route
onto Macie's PATH. r5 read a hand-written workaround as an artifact to delete; it was
the opposite, and `setup.sh` on a fresh machine never reproduced it — which is why the
reverse enrollment failed on the host that lacked it.

**The `fredrir@archie` workaround is moot: nothing enrols the opaque alias any more.**
The route split (`1a522dc`, then today's re-enrollment) addresses each transport by
endpoint, so `archie` — whose transport an ssh-config `Match exec` probe chose
invisibly — is no longer a route anyone spells. Macie holds `fredrir@10.77.77.2` (usb,
priority 10) and `fredrir@100.126.231.24` (tailscale, priority 20), with the old
`archie` row kept at `enabled=0` rather than deleted; Archie holds `fredrir@10.77.77.1`
(usb) and `fredrir@100.75.71.79` (tailscale), both enabled and last reporting `ok`.
The behaviour r5 described is itself unchanged: `upsert_route` writes `username`
unconditionally, so a bare `dmux ssh <endpoint>` still clears it on an existing row.
The scenario retired, not the defect.

**The two-host defect is fixed, and not where r5 pointed.** `142cff5` pins the remote
proxy: the owner reports its managed socket as a `wez:socket:` capability token,
`gui.rs` builds and validates the strict-endpoint `override_proxy_command`, and
`shared/wezterm/wez/remote/mux.lua` assigns it. `publish_persistent_domains` in
`wez/dmux_bridge/init.lua` was never touched — it consumes domain rows, it does not
build the proxy command. The `two_host` case itself is still unrun: no r6 release
exists and r5 is still phase `mac_deployed`.

**The r2 SSH wrapper is gone.** `/tmp/dmux-rollout-ssh-r2-a8c4` is absent on both hosts
and referenced nowhere in the repo; Archie's mux has restarted since (PID 957, not
r5's 1347078). Nothing left to clean up.

**Still true, re-verified today.** The orphan Space `01a01220-…`
(`w6mac-smoke-20260817-archie`) is `active` and `healthy` in Archie's registry, so
r6's collision risk stands. The `01a011fe…` tombstone and Archie's
`dmux-rollout-29156c98-preserve-ssh-path` stash are intact.

**Service evidence is r5-era, not current.** The Mac row's PID 5458 is gone — the mux
is PID 54528 today — while `backend_instance_uid` `6ef8d4c9-…` is unchanged, which is
the identity that row was making a claim about. Both registries still carry the r5-era
`server_pid`/`server_epoch` for their backend instance, so those columns are not
evidence of what is running now.
