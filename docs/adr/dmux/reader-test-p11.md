## Reader's answers (verbatim; headings demoted one level)

Sources used: `docs/dmux-wezterm-first-plan.md` (cited as §N) and `docs/adr/dmux/**` (ADRs 003, 010, 012; `report/04-fence-and-instance-states.md`; `evidence/spike3-gui-bridge.md`). Nothing else was consulted.

### A. Human reference grammar and `--row`

1. **Precedence and unknown host token.** The grammar fixes a structural precedence: (1) canonical URI `dmux://…`; (2) full HostUid plus SpaceNo (`<host-uuid>:2`); (3) expanded alias/label plus SpaceNo (`b:2`); (4) bare digits as local SpaceNo (`2`); (5) compact alias plus digits (`b2`); (6) host-qualified logical name (`b:project`, `archie:project`); (7) bare logical name on the resolved/current host only. A `<host-token>:<digits>` form is always parsed as an owner-qualified numeric ref before any name lookup, so an unknown or tombstoned host token is an error; dmux never falls back to treating it as a logical name.
   Citations: §6.2 — "Parsing precedence is structural: 1. Canonical URI. 2. Full HostUid plus SpaceNo. …"; "Any `<host-token>:<digits>` is parsed as an owner-qualified numeric ref before name lookup. An unknown/tombstoned host token is therefore an error, never a fallback to a logical name."

2. **`07` and `a0`.** Neither is a valid Space reference. `07` matches the bare-digit class `^[0-9]+$`, so it is ID-shaped (SpaceNo-shaped), but SpaceNo is canonical nonzero decimal `[1-9][0-9]*`, so a leading-zero form is an invalid ref and is not reinterpreted as a name. `a0` matches the fixed lexical class `^[A-Za-z]+[0-9]+$` (compact alias `a` plus digits), so it is ID-shaped too, but SpaceNo `0` is invalid, so it is likewise an invalid ref, never a logical name. The classification is purely lexical — it applies "even when the apparent alias is not currently enrolled" — so enrolling or forgetting hosts cannot move either string between the ID and name classes.
   Citations: §6.2 — "`SpaceNo` is canonical nonzero decimal `[1-9][0-9]*`; `0` and leading-zero forms are invalid refs and are not reinterpreted as names."; "The fixed lexical class `^[A-Za-z]+[0-9]+$` and bare `^[0-9]+$` are ID-shaped even when the apparent alias is not currently enrolled; this classification never changes as hosts are added."

3. **Row targeting during the compatibility window.** During the one-release window an operator targets a Space by listing position only with the explicit `--row N` escape; a bare digit means the permanent local SpaceNo immediately. A deprecated row index cannot silently hit a different Space because bare digits are never parsed as rows (precedence item 4 makes them SpaceNo), SpaceNo is "Permanent; never reused" (§6.1), so a number copied from an old listing resolves to the Space that owns that number or fails as not-found/deleted, and listings are sorted "by host enrollment order and permanent SpaceNo, never by a transient row index", so the number displayed is the stable identity itself. Row semantics must be requested explicitly with `--row`, and ADR 012's dispatch log records that `--row` refuses its tail (`backend_epoch_changed`) when the listing is incomplete rather than guessing.
   Citations: §17 item 13 — "Enable a one-release `--row N` compatibility escape. Bare digits immediately mean permanent local SpaceNo."; §20.2 case 44 — "Deprecated row indices cannot silently target a stable ID; `--row` is explicit during compatibility."; §16.1 — "Sort by host enrollment order and permanent SpaceNo, never by a transient row index."; §6.2 precedence item 4 "Bare digits as local SpaceNo"; §6.1 SpaceNo "Permanent; never reused"; ADR 012 §10 (A5-d close) — "`--row` refuses its tail with `backend_epoch_changed` and names nothing adoptable".

4. **Connecting to a Space named `ls`.** The CLI provides `con --name NAME` (e.g. `dmux --host archie con --name ls`), the exact-name escape "for an adopted legacy name that looks like a ref or subcommand". Its two restrictions: it is mutually exclusive with a positional Space ref, and it never performs fuzzy or cross-host search. The wrapper `ssa ls` does not create a Space: a lone bare word that is a dmux subcommand or alias is forwarded verbatim as that subcommand, so `ssa ls` lists (`dmux --host archie ls`); the wrapper's verb allowlist is mechanically held equal to the CLI by `the_wrapper_verb_allowlist_matches_the_cli`. ADR 010 §4 adds that a Space genuinely named after a verb is reached by spelling the verb (`ssa new ls`), and notes `con --name` is connect-only and gated on `DMUX_WEZ_FIRST` until the cutover.
   Citations: §7.4 — "`--name` is the exact-name escape for an adopted legacy name that looks like a ref or subcommand. It is mutually exclusive with a positional Space ref and never performs fuzzy or cross-host search."; §17 — "A lone bare word that is a dmux subcommand or alias is that subcommand, so `ssa ls` lists"; ADR 010 §4 — "A listed verb is forwarded verbatim — the list decides *not to create*"; "Spell the verb: `ssa new ls` creates-or-connects one named "ls"."

### B. Automatic creation decision

5. **Enrolled USB route, probe times out.** Neither backend is created; selection refuses. A timeout during eligibility preflight is not a positive `route_absent`/`usb_link_down` observation, and only such a positive observation makes USB ineligible and permits automatic tmux; an unplugged cable seen through a TCP/SSH probe is indistinguishable from a transient network failure, so choosing tmux would be the silent backend substitution the plan forbids. This is acceptance case 17b.
   Citations: §8.3 — "DNS failure, refusal/reset, and timeout are not proof of "unwired"; during eligibility preflight they return route unavailable rather than choose tmux."; ADR 010 §1 — "17b — enrolled USB route present, eligibility probe fails → refuse, create neither backend."; §20.2 case 17b.

6. **No USB route enrolled at all.** A tmux Space is created. The permitting observation is a positively observed pre-selection `route_absent` — "no enrolled USB route" — which is the one situation (besides an authoritative link-state signal) that makes USB ineligible before selection and allows automatic tmux; in the §8.3 table this is the "Remote USB route absent/unwired → tmux" row. This is acceptance case 17a.
   Citations: §8.3 — "Only a positively observed pre-selection `route_absent`/`usb_link_down` (no enrolled USB route or an authoritative link-state signal) makes USB ineligible and permits automatic tmux selection."; ADR 010 §1 — "17a — no enrolled USB route → positive `route_absent` → automatic tmux."

7. **Host-key mismatch after Wez was selected.** dmux may not try the Tailscale route and may not create a tmux Space: host-key failure is a terminal class, and no failure class ever permits backend fallback. After Wez is selected, another enrolled route may be tried only for a pre-authentication transport failure — DNS failure, no route, connection refusal/reset, or connect-stage timeout. Before continuing on the alternate route it must verify the expected HostUid, RegistryUid, backend-instance identity/epoch, SSH trust, and a compatible protocol. Route failover is a same-host, same-backend-instance operation only.
   Citations: §8.3 — "After Wez is selected, another enrolled route may be tried only for a pre-authentication transport failure: DNS failure, no route, connection refusal/reset, or connect-stage timeout. Before continuing, the alternate route must verify the expected HostUid, RegistryUid, backend-instance identity/epoch, SSH trust, and compatible protocol. Host-key, identity, authentication, permission, protocol/version, malformed-response, server, native-mutation, and postcondition failures are terminal. … None of these cases permits backend fallback."; §2.9 — "Route failover may change USB to Tailscale only while staying on the same verified host and backend instance. Backend fallback is never a route operation."; §1 — "Once Wez has been selected, an authentication, protocol, compatibility, or mutation failure never silently creates a tmux Space."

8. **Indeterminate Wez inventory, auto vs explicit tmux.** With automatic backend, a complete tmux inventory with no match plus an `unreachable` Wez inventory creates and attaches nothing: the result is a typed fail-closed refusal, because auto lookup requires determinate inventories from both providers and every path that may create requires both. With `--backend tmux` and exactly one selectable live tmux match, dmux selects and connects that match even though Wez is indeterminate. They differ because the explicit backend constraint is authoritative for a non-creating selection — neither creation nor cross-backend ambiguity resolution is needed — whereas auto mode cannot exclude a same-named Wez Space, and §2.10 says an unavailable inventory is never an empty one; the explicit form still could not create if there were no tmux match (case 7).
   Citations: §8.2 — "Auto lookup requires determinate inventories from both providers; one known match plus one indeterminate provider cannot exclude ambiguity. With explicit backend `B`, a complete `B` inventory containing an exact live match may select that match even if the opposite provider is indeterminate, because neither creation nor backend ambiguity resolution is needed. Every path that may create requires determinate inventories from both providers."; §8.2 step 7 "selectable result on `B`: select it irrespective of the opposite provider"; §2.10 — "A failed or partial inventory is not an empty inventory. Creation fails closed when dmux cannot rule out an existing same-named Space."; §20.2 case 7.

9. **`new foo --backend wez` against a tmux `foo`.** With a managed, live, healthy tmux `foo` as the only exact match, the command returns a name-conflict error (exit 4) and creates nothing; adding `--allow-name-collision` changes the outcome to validating `foo` and creating a Wez Space beside the tmux one (the flag never changes a Space's backend). If the tmux match is an unmanaged native session, the flag does not help: an opposite unmanaged/blocking result returns conflict/repair-required even with `--allow-name-collision`, so the session must be adopted or repaired first.
   Citations: §8.2 step 7 — "no result on `B`, selectable managed result only on the opposite backend: name-conflict error, or validate/create on `B` only with `--allow-name-collision`; no result on `B` plus an opposite unmanaged/blocking result: return conflict/repair-required even with `--allow-name-collision`"; §2.12 — "Intentional creation beside an opposite-backend match additionally requires `--allow-name-collision`."; §7.4 — "`--allow-name-collision` is an explicit expert acknowledgement and never changes a Space's backend."

### C. Registry lock ordering

10. **`rename` lock order.** In acquisition order: (1) the authority-gate kernel lock, shared; (2) the decision locks `decision:<owner>:<sha256-of-exact-name-bytes>` for the old and new names, taken in exact-byte lexical order (one per name, serializing all same-name operations on the owner); (3) the common backend-instance kernel lock, exclusive; (4) any Space lock. Release is in reverse order. A decision lock may never be acquired after a backend-instance or Space lock.
    Citations: §10.1 — "All operations first take a shared authority-gate kernel lock … A normal name-changing mutation then takes decision locks (`decision:<owner>:<sha256-of-exact-name-bytes>`) in exact-byte lexical order, the common backend-instance kernel lock in exclusive mode, and any Space lock, releasing in reverse. … No operation acquires a decision lock after backend/Space."; §8.2 — "Rename takes decision leases for old and new names in lexical byte order."

11. **`ls` vs `adopt` on the backend-instance lock.** `dmux ls` takes the backend-instance kernel lock shared (inventory is a read); `dmux adopt` takes it exclusive, since adoption/reconciliation mutation uses the same backend-instance exclusive lock as ordinary backend mutation and recovery. Only `adopt` takes decision locks — the owner-wide decision lock for the proposed logical name, acquired before the backend lock; `ls` takes none because it is semantically read-only and never allocates identity. Neither takes the authority gate exclusively: every operation takes it shared, and only maintenance (schema migration under its exclusive maintenance lease) takes it exclusively, which is why maintenance overlaps nothing.
    Citations: §10.1 — "Inventory takes a backend-instance lock shared."; "Recovery, snapshot publication, adoption/reconciliation mutation, and ordinary backend mutation all use the same backend-instance exclusive lock"; "maintenance takes that same gate exclusively and therefore overlaps nothing"; §10.3 — "Adopt, rebind, normalization that allocates identity, and migration take the owner-wide decision lock for the proposed logical name before the backend lock"; §2.7 — "`dmux ls` is semantically read-only … never allocates identity, changes lifecycle, or mutates a native resource."

12. **Expired lease with a paused holder.** No. Wall-clock expiry alone never authorizes takeover; a paused live holder still retains its POSIX `fcntl` kernel lock and cannot be timed out or superseded, and a hung holder must be explicitly diagnosed and terminated. What proves a prior holder cannot resume native work is not the clock but the takeover sequence: the taker verifies the prior holder's recorded PID/start token no longer owns a process or coordinator, and then actually acquires the non-stealable kernel lock — "acquiring the kernel lock proves it cannot later resume native work" — after which it atomically advances the database fencing token and assigns itself as holder, rechecking that token before every native-ID action.
    Citations: §10.1 — "SQLite rows record ownership/recovery; POSIX `fcntl` locks provide non-stealable exclusion. Clock expiry alone never authorizes takeover."; §10.2 — "A paused live holder retains the kernel lock and cannot be timed out/superseded. A hung holder must be explicitly diagnosed and terminated; expiry alone never permits concurrent native mutation."; §10.2 steps 2–3 — "For a different prior holder, verify its recorded PID/start token no longer owns a process/coordinator; acquiring the kernel lock proves it cannot later resume native work. 3. Atomically advance the database fencing token and assign the new holder."

### D. Bridge origin kinds and authorization

13. **Origin kinds.** The two kinds are `origin.kind=in_gui` and `origin.kind=cold_launcher`. `in_gui` must bind the origin GUI instance, pane and domain plus the revalidated origin HostUid, SpaceUid and server epoch. `cold_launcher` is allowed only for an explicit `--launch-gui`, carries no fabricated pane or Space, and instead binds the current UID, the broker-authenticated client PID/start token, the launcher request, and the intended target domain/backend instance. Every action that requires a current pane rejects `cold_launcher`.
    Citations: §13.2 — "`origin.kind=in_gui` requires origin GUI instance/pane/domain plus the revalidated origin HostUid/SpaceUid/server epoch; `origin.kind=cold_launcher` is allowed only for explicit `--launch-gui`, has no fabricated pane/Space, and instead binds the current UID, broker-authenticated client PID/start token, launcher request, and intended target domain/backend instance. Actions requiring a current pane reject `cold_launcher`."; ADR 003 §3 table — "Origin variants | `in_gui` and `cold_launcher` per §13.2; actions requiring a pane reject `cold_launcher`".

14. **Valid signature, fresh nonce, unexpired TTL, but consumed UID.** The GUI treats it as a replay and does not execute the action again: the request UID is in the consumed-uid set (and the consumed request file has been renamed), so the request is refused. The original acknowledgement for that UID is preserved byte-identical for idempotent re-read, and the GUI writes a distinct error document with `ok=false, error="replayed"`. The requester therefore receives the `replayed` error rather than a fresh success, and per §13.2 a replayed acknowledgement fails closed on the client side; a valid HMAC, nonce and TTL do not override the one-use replay key.
    Citations: §13.2 — "Every bridge action uses a signed or broker-issued, one-use token containing … nonce, replay key"; "Timeout or malformed/replayed acknowledgement fails closed."; ADR 003 §3 — "replay → original ack preserved byte-identical plus a distinct `replayed` error doc"; "Replay persistence | consumed-uid set in GUI memory + consumed request files renamed; acks preserved for idempotent re-read"; evidence/spike3 — ack `{"error": "replayed", "ok": false, …}`.

15. **Activating a missing opaque workspace key.** The bridge must use the pcall-wrapped `wezterm.mux.set_active_workspace(name)` primitive, and the required result is `not_found` with an owner-side diff of zero — nothing created — because that primitive raises on a missing workspace and creates nothing, so it fails closed even when the pre-check is stale. `SwitchToWorkspace` is banned from every activation path because `SwitchToWorkspace { name = <missing> }` silently creates an owner workspace, window and pane, which violates `con`-never-creates; a check followed by the switch is insufficient because the target can vanish between the two callbacks, as the deterministic split test proved.
    Citations: §13.2 — "atomically activate an already-existing opaque workspace, returning not-found if absent. A check followed by `SwitchToWorkspace` or `connect --workspace` is insufficient because the switch may create the workspace and violate `con`-never-creates."; ADR 003 §2 — "Hazard confirmed: `SwitchToWorkspace { name = <missing> }` silently creates an owner workspace+window+pane. Banned from all activation paths."; "Selected primitive: pcall'd `wezterm.mux.set_active_workspace(name)` — it raises on a missing workspace and creates nothing, so it fails closed even when the pre-check is stale."; "`not_found` with owner diff-zero".

### E. Cold-recovery eligibility

16. **Sentinel plus one user pane.** No manifest is restored. Step 3 requires the in-process tree to contain exactly the valid sentinel and zero user panes; one user pane makes the server nonempty, so recovery is ineligible, nothing is restored, and startup still completes (readiness succeeds with the existing panes untouched). This is the plan's core guard that cold recovery only ever restores into a new, empty owner mux — "A nonempty server never restores."
    Citations: §15.3 step 3 — "Inspect `wezterm.mux.all_windows()` in-process. Require exactly the valid sentinel and zero user panes"; §15.3 — "If recovery is ineligible or no manifest qualifies, the sentinel remains as the only pane and readiness still succeeds."; §22 — "cold recovery restores only a new empty owner mux and honors intentional empty state"; §20.2 case 36 — "A nonempty server never restores."

17. **Manifest revision 41 vs `intentional_empty_revision` 43.** It is not restored: step 4 loads only the newest complete manifest whose registry revision is newer than the instance's `intentional_empty_revision`, and 41 is at or before 43. `intentional_empty_revision` is recorded, per Wez backend instance, by the removal of the final active user Space, and only under the proof of a complete same-epoch scan showing zero user panes. A later mux startup never restores a manifest at or before that revision.
    Citations: §15.3 step 4 — "Load the newest complete manifest for this backend instance whose registry revision is newer than that instance's `intentional_empty_revision`."; §15.3 paragraph after step 9 — "Removing the final active user Space records `intentional_empty_revision` only after a complete same-epoch scan proves zero user panes; the marker is per Wez backend instance. A later mux startup never restores a manifest at or before that revision."; §20.2 case 37.

18. **Crash after two of five Spaces restored.** No: the coordinator on the next start does not begin a fresh restore. The crash leaves the recovery lease and node journal observable, so the next starter takes over under §10.2 fencing (verifies the prior holder's PID/start token is gone, acquires the kernel lock, advances the fencing token, performs a complete provider scan and reconciles the predecessor's journal) and resumes the same generation. For the half-restored tree, each manifest node is reconciled against the journal and the native tree/token title: a node proven created by that generation is completed, a recovery-created bootstrap partial is safely removed or replaced, and nothing is guessed by list ordinal or duplicated. An abort may remove only nodes proven to belong to that recovery generation and never deletes pre-existing native state.
    Citations: §15.3 — "A crash leaves the recovery lease/journal observable. Takeover follows §10.2 fencing and resumes the same generation; it does not start a new blind restore."; §15.3 step 7 — "A resumed generation either completes a node proven to have been created by that generation or safely removes/replaces only a recovery-created bootstrap partial; it never guesses by list ordinal or duplicates a Space/Group/Split."; §15.3 — "Abort may remove only nodes proven to belong to that recovery generation; it never deletes pre-existing native state."; §10.2 steps 2–4 — "perform a complete provider scan and reconcile the predecessor's journal/postcondition. Continue only from a proven state; otherwise mark `unknown`/`conflict`."

### F. Backend-instance states A–F and their remedies

19. **The six states and the historical collapse.** A: not registered (no row). B: registered without an endpoint (`socket_path` NULL). C: registered, unpublished (epoch NULL), idle — lease free. D: registered, unpublished, with the exclusive instance lease/lock held (a bootstrap or recovery in flight). E: published and the live server agrees. F: published but the live server disagrees or the published process is dead (`stale_incarnation`). `ls` historically collapsed C and D (the "confirmed defect"), emitting the same advice for both. The two observations that now separate them are the non-blocking shared `try_acquire` on the backend-instance kernel lock (the fence) and `Registry::current_lease(&LeaseScope::Recovery(instance))` (the recovery lease) — the lease probe; E is separated from F by the liveness probe.
    Citations: §5.2 — "A not registered; B registered without an endpoint; C registered, unpublished, idle; D registered, unpublished, with the exclusive instance lease held (a bootstrap or recovery in flight); E published and the live server agrees; F published but the live server disagrees or the published process is dead (`stale_incarnation`)"; "`dmux ls` and `dmux doctor` distinguish C from D (lease probe) and E from F (liveness probe) and never collapse them."; report 04 — "The C/D collapse is the confirmed defect."; "Both distinguishers ls needs are already available and unused — the same non-blocking shared `try_acquire` it takes for `Managed`, and `Registry::current_lease(&LeaseScope::Recovery(instance))`."; ADR 012 §5 WS-B.2 — "`ls` consults the non-blocking shared `try_acquire` and `Registry::current_lease(Recovery(instance))` for an `Unpublished` target before choosing advice."

20. **Published epoch E / pid 5458 dead, live mux serves X.** That instance is in state F (`stale_incarnation`). `ls` renders its Spaces with `observation: unreachable` and `detail: stale_incarnation` (never `owner-proven server stopped`, because nothing verified has answered). 21. **Remedies for state F and the explicit clear.** Two remedies: restart the managed service, permitted only when the mux holds no user panes (stopping a server with user panes is destructive); otherwise `dmux repair retire-incarnation`, once the service is confirmed down — the operator's move "when the managed service will not come back managed". The explicit clear, `dmux repair retire-incarnation --backend <wez|tmux> --epoch <UUID> [--allow-live-pid] [-y]`, is expert, confirmed and owner-local: it compares-and-sets on the published epoch (the supplied `--epoch` must equal the row's published epoch, otherwise it refuses), the retirement is journaled as a revision that advances the revision chain like `publish_backend_server`, and it refuses a still-live pid without `--allow-live-pid` and any unfinished recovery generation. 22. **Registered tmux instance, no epoch, lease free, lock not held.** That is state C: registered, unpublished, idle. `ls` should advise running the bootstrap (`dmux _tmux-bootstrap`, or bringing the server under management through explicit `new`/`adopt`/migration) or waiting for the service to coordinate, and it lists the sessions as `unmanaged:unepoched` with no Group/Split refs because `ls` never sets the epoch option itself.
